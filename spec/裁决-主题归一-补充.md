## 一、kernel-dev 的三条异议，两条成立

### 异议 1：`D0cA.model_called_on_counter` 不区分「没调」和「调了但被挡」——**成立，改判据**

现状：模型被调过，但输出因 `copied_from_source` / `relation_polarity` 被丢，判据记成「没调」。

**裁决**：判据拆成两条。
- `D0cA.model_was_called` —— 模型确实被调用过（不管输出收不收）
- `D0cA2.output_was_usable` —— 输出被采纳过至少一次

这两件事是不同的问题：前者测「链有没有接上」，后者测「判据是不是太严」。**混成一条，就分不清是链断了还是闸太紧。**

### 异议 2：换谓词就换槽，是裁决一的代价——**成立，不改**

模型理解变了，主题槽跟着变，这是**正确的行为**，不是丢累积。规格本来就说主题该跟着判断走。

**裁决**：`B7` 类判据的 `from ≥ 2` 要求，**只对「同一槽内」成立**。跨槽不要求累积。这一条写入规格，不许再拿它冤枉内核。

### 异议 3：`f` 的陌生说法进不了门，只能加回关键词——**部分成立，暴露了裁决一的漏洞**

他说得对：假模型给的主题名是 `t_sleep`，骨架只有「他」一个字，按「骨架重合」认不出来。

**但这不是裁决错了，是裁决一漏了一路。** 裁决一写了「或模型在熔的时候自己指定主题」，可内核里**这条路没真正实现**。

## 二、裁决二：把「模型自认主题」真正落地

### 硬要求

`synth.synthesize()` 的返回值**必须**包含主题归属，二选一：

```jsonc
{ "theme": "still_thinks_about|他" }   // 自己指定一个主题键
{ "themeOf": "<现役判断 id>" }         // 或直接指向某条现役判断，说「我说的是这件事」
```

**内核必须接受这两条路**，不能只认骨架重合。

### 为什么这不是回潮

关键词表是「**内核**按字面猜主题」。
模型自认是「**她**想完了自己说这是同一件事」。

前者是存储体的做法——字面对上就算。
后者是脑子的做法——她理解之后自己归类。

**差别在于谁来做这个判断。** 内核不再猜，把归类权交给「想」的那一层。

### 附带约束（防止变成万能后门）

1. 模型自认的主题键，**必须能对上一条现役判断**，对不上就当新主题——不许凭空造槽。
2. **不许把输入原句塞进 `theme`**。判据同 `subject`：连续 8 字重合即废。
3. 模型自认的主题，与骨架重合的结果**冲突时以模型为准**，但要记一笔 `themeSource: 'model'|'skeleton'`，方便以后查它是不是乱认。

## 四、`f` 的新口径（重要）

`min=3`（五种说法收敛三种）**不动**。但要求 report 里必须分开报：

```
F1a  骨架重合能收敛几种   —— 低于 2 说明骨架特征太弱
F1b  模型自认能收敛几种   —— 这才是裁决二真正要测的
F3   两条路都失败的有几种 —— 这些是真丢
```

三个数分开看，才知道该修骨架还是修自认。
