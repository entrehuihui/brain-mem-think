## G1 · `clause()` 拿不到 `tension.why`

**位置**
- `src/flash.mjs:61-71` —— `export function clause(note)`
- `src/flash.mjs:27-58` —— `export function toNote(b)`（`tension` 在 `src/flash.mjs:43` 已经导出了）

**现状**

`clause()` 只读三个字段：

```
const s = typeof note === 'string' ? note : note?.note;      // :62
const status = typeof note === 'string' ? 'held' : note?.status; // :63
const was = typeof note === 'object' ? note?.was?.text : null;   // :67
```

`tension` 虽然在 `toNote()` 里被复制出来（`src/flash.mjs:43`：`tension: b.tension ? { ...b.tension } : null`），但 `clause()` 一次都没有读它。

**为什么挡路**

宿主注入块里「悬而未决」那一类要写三层（见 `spec/插件壳.md` §3.3a）：

```
还没想明白：<判断正文>——<tension.why>
这回它又碰上来了一次：<probe>（已碰第 n 次…）
```

第一层的「——为什么悬着」现在**无处可取**。`tension.why` 的值在内核里是有的：

- `src/judge.mjs:303` —— `transition()` 转到 `PENDING` 时写 `belief.tension = belief.tension ?? { since: at, why: '还没定下来' }`
- `src/mind.mjs:305` —— `#birth()` 里 `setTension(b, { since: this.now(), why: '才碰上一条，不下结论' })`
- `src/judge.mjs:322-325` —— `setTension()` 本身

也就是说**素材齐了，只是没接出来**。缺这一句，注入层只能退化成「还没想明白：<判断正文>」，而那就正好是任务书点名不许的「念清单」。

**要求改成什么**

`clause()` 增加对 `tension` 的读取，`open` 分支的形态改为（对应 `spec/插件壳.md` §3.3a 第一层）：

| 条件 | 输出 |
|---|---|
| `tension.why` 存在且非空 | `还没想明白：${s}——${tension.why}` |
| `tension` 为空 / `why` 为空 | `还没想明白：${s}`（**不补默认话**，不许自己编一句「感觉就是」） |

**验收判据（可直接写进单测）**

1. 造一条 `status=pending` 且 `tension.why='才碰上一条，不下结论'` 的 note → `clause(note)` 必须同时含判断正文和 `'才碰上一条，不下结论'`。
2. 造一条 `status=pending` 且 `tension=null` 的 note → `clause(note)` 输出必须**不含**任何 `——` 后的自造理由，且含 `还没想明白`。
3. `clause()` 仍不许因为 `tension` 缺失而抛。

## G2 · `open` 是将来时、`retired` 被压成一行

**位置**
- `src/flash.mjs:65` —— `open` 分支
- `src/flash.mjs:66-69` —— `retired` 分支

**现状**

```js
if (status === 'open') return `还没想明白：${s}——这回碰上同一样事，我会想一下。`;   // :65
if (status === 'retired') {
  const was = typeof note === 'object' ? note?.was?.text : null;
  return was ? `我曾经以为${was}，后来我改了口：${s}。` : `我曾经这么以为：${s}。`;      // :68
}
```

**为什么挡路 —— 两处，都是语气级的硬伤**

**(1) `open` 的「我会想一下」是将来时。** 注入进系统提示之后，她就真的只是「想一下」，下一轮她手里没有新东西可依据。等价于**喂给她一个承诺，而不是一次思考**。规格要的是「这次想确认什么」（`spec/规格主轴.md:294` 的 `probe` 字段、`:305` F4-c「每轮 `probe` 必须与上一轮字符级不同」），不是「我会想一下」。

**(2) `retired` 把「以前」和「现在」压成同一句的转折。** 读者（也就是她）只看到「我现在信 X，我以前信 Y」，两句话变成**一个句子的转折**，语气被动。真正要她带上的是**改的过程**，不是改的结果。

而且 `retired` 分支还丢了一样东西：`was.why`。`src/revision.mjs:104-111` 存 `was` 的时候是带 `why` 的（`src/revision.mjs:105`：`why: note.why`），`clause()` 只取了 `was.text`。

**要求改成什么**

对应 `spec/插件壳.md` §3.3(c) 的三行形态。`clause()` 是「一句话」的接口，撑不下三行，所以：

> **要求：`clause()` 保持「单一职责、只出一行」，另加一个多行接口**，例如 `lines(note)` → `string[]`：
> - `open` → 一行：`还没想明白：<正文>——<tension.why>`（这一行与 G1 合并）
> - `held` → 一行：`<正文>`
> - `retired` → 三行：`我以前这么以为：<was.text>` / `后来不这么想了：<retiredBecause>` / `现在我是这么想的：<正文>`

**`clause()` 自身的最小修正（不改接口也能做）**

- `open` 去掉「我会想一下」这句将来时承诺，改成陈述：`还没想明白：${s}——${tension.why}`（见 G1）。
- `retired` 不再写「我曾经以为…，后来我改了口：…」这种压缩句；若暂不拆三行，至少改成两句并列：`我以前这么以为：${was}。现在我是这么想的：${s}。`

**验收判据**

1. `clause()` 的任何输出**都不许含「我会」「以后」「下次」**这类将来时承诺（打一条正则 `/(我会|以后|下次)/` 必须为空）。
2. `retired` 的 `lines(note).length === 3`，且第 1 行含 `was.text`、第 2 行含 `retiredBecause`（或 `overturnedReason`）、第 3 行含当前正文。
3. `retired` 且 `was=null` 时（理论上 `toNote()` 会从 `turns[0]` 补，见 `src/flash.mjs:51-56`），`lines()` 不许抛，且至少给出「现在」这一行。

## G3 · `digest()` 把 `open` 排在最后

**位置**
- `src/flash.mjs:136-146` —— `digest({ maxOpen = 2, maxHeld = 3, maxRetired = 1 })`
- 具体三句的次序在 `src/flash.mjs:140`（held）、`:141-143`（retired）、`:144`（open）

**现状**

```js
for (const b of pick(STATUS.HELD, maxHeld)) lines.push(clause(toNote(b)));      // :140
for (const b of pick(STATUS.ESTEEMED, ...)) lines.push(clause(toNote(b)));      // :141-143
for (const b of pick(STATUS.PENDING, maxOpen)) lines.push(clause(toNote(b)));   // :144
return { lines, text: lines.join('\n') };                                       // :145
```

顺序是 **held → retired → open**，`open` 永远垫底。

**为什么挡路**

`open`（悬而未决）是**最该被她带在身上过这一轮**的东西 —— 它是唯一一类「这一轮需要被推一下」的判断。垫底的位置意味着：宿主一旦按「前 N 行」截断（`spec/插件壳.md` §3.7 第 2 条：总行数 ≤ 8），悬案第一个被砍。

而 `retired` 恰恰相反：它是「已经想完的旧账」，摆在最前面会让她一上来就沉浸在过去。

**要求改成什么**

`digest()` 的次序改为 **open → held → retired**，并且：

- `open` 的默认配额保持 `maxOpen = 2`（不要放太多，见 `spec/插件壳.md` §3.6 第 1 步「悬案最多摆一条，且必须带 probe」—— 宿主层还会再筛一次，`digest()` 给 2 条是给宿主留选择余地）。
- `retired` 的默认配额从 `maxRetired = 1` 降到 **1**（现状已经是 1，明确保留；`spec/插件壳.md` §3.3(c) 第 3 条要求「同一主题只摆最近一条」）。

**验收判据**

1. 库里同时有 1 条 held、1 条 retired、1 条 open → `digest().lines[0]` 必须来自 `open` 那条。
2. `digest().lines.length <= maxOpen + maxHeld + maxRetired`。
3. 三条的顺序必须与本次调用的配额次序一致（打乱 `maxOpen` 为 0 时，`lines[0]` 必须来自 held）。

## G4 · `curiosity` 的 `overweight` 被 `mind` 丢掉

**位置**
- `src/curiosity.mjs:74-81` —— `questions.push({ ... overweight: (note.weight ?? 0) >= o.maxWeight })`
- `src/mind.mjs:125-131` —— `base.triggered = touched.questions.map((q) => ({ id: q.id, asked: q.asked, push: q.push }))`
- `src/flash.mjs:99-106` —— `pendingQuestions()` 的返回字段

**现状**

`curiosity.inspect()` 产出的 `questions[]` 里每项有 `id / note / themeKey / asked / push / overweight`（`src/curiosity.mjs:74-81`）。`mind.ingest()` 只在 `src/mind.mjs:131` 把 `id / asked / push` 三个字段留下，**`note` / `themeKey` / `overweight` 全丢了**。`flash.pendingQuestions()` 又是另一条路，只吐 `note / themeKey / asked / since / why`（`src/flash.mjs:99-106`）。

结果：**两条路都拿不到 `overweight`。**

**为什么挡路**

`overweight` 的定义是「这条悬案的份量已经压到了 `maxWeight`（默认 0.75，`src/curiosity.mjs:21`）」。它是「该不该放弃追问」的一个现成信号 —— 一条悬案份量越压越重却迟迟定不下来，正是该往 `retired` 走的时候。

宿主注入层要用它写「第 N 次还是定不下来就认了」这一行（`spec/插件壳.md` §3.6 第 (三) 步）。现在没有这个信号，注入层只能靠数字数（第几次碰），在份量还轻的悬案上也会说「要认了」——**假催，比不催难看**。

**要求改成什么**

两条路各补一处，二选一即可（建议都补，因为两条路用途不同）：

1. **`mind.ingest()` 的返回值**（`src/mind.mjs:131`）保留 `overweight`：
   `base.triggered` 每项改为 `{ id, asked, push, overweight }`。
   —— 用途：**当轮**注入层知道「这一次碰它，已经压到位了」。

2. **`flash.pendingQuestions()`**（`src/flash.mjs:99-106`）暴露份量与信号：
   每项增加 `weight: b.weight` 与 `overweight: (b.weight ?? 0) >= 0.75`（阈值应与 `src/curiosity.mjs:20` 的 `maxWeight` 同源，别写死两份）。
   —— 用途：**跨轮**注入块拼装时，不需要再进一次 `inspect()` 就能判断。

**验收判据**

1. 造一条 `weight=0.8` 的 pending note，跑一次 `mind.ingest()` 触发它 → 返回的 `triggered[0].overweight === true`。
2. 造一条 `weight=0.2` 的 pending note 做同样的事 → `overweight === false`。
3. `flash.pendingQuestions()` 每项都有 `weight` 与 `overweight` 字段，且 `overweight` 的阈值与 `curiosity` 的 `maxWeight` 一致（改一处另一处跟着变，不许两处硬编码同一个数）。

## G5 · `maxPush` 默认 6，规格要求 ≤ 3

**位置**
- `src/curiosity.mjs:20-22` —— `CURIOSITY_DEFAULTS = { cooldownBeats: 1, maxPush: 6, maxWeight: 0.75 }`
- 规格：`spec/规格主轴.md:301`（F4-b「同一 `open` 判断的触发次数 ≤ 3」）、`spec/规格主轴.md:318`（第 3 次仍不落判 → 转 `retired`，`retired_reason = "追了三次都没拿到准信，认了"`）

**现状**

内核允许一条悬案被推 **6** 次（`src/curiosity.mjs:20`），规格只许 **3** 次且第 3 次必须收口。

`src/curiosity.mjs:70` 的判断是 `if ((note.curiosityFired ?? 0) >= o.maxPush) continue;` —— 即第 7 次开始不再推。规格要到第 4 次就不许再推。

**为什么挡路**

宿主注入层要写「已碰第 N 次，M 次还定不下来就认了」。`M` 从哪来？

- 按内核：6
- 按规格：3

**两处都写死，说出来的数就一定跟另一边不一致。** 而且规格那句话不是建议，是 F4-b/F4-d 的判据，验收脚本会照它判红。

**要求改成什么**

**二选一，由内核负责人定，然后另一处改掉：**

- **方案甲（建议）**：内核向规格靠。`CURIOSITY_DEFAULTS.maxPush` 改为 **3**；并且补上「第 3 次仍不落判 → `retired` + `overturnedReason = '追了三次都没拿到准信，认了'`」这条收口（现在内核里没有这段逻辑，`inspect()` 只管「推不推」，不管「推完之后怎么办」）。
- **方案乙**：规格改数（不推荐 —— 规格是被验收脚本硬编码的，改规格等于改验收）。

无论选哪个，**注入层要能从接口读到「还剩几次」**，不许自己算。建议 `flash.pendingQuestions()` 每项补 `left: maxPush - asked`，或直接补 `maxPush`。

**验收判据**

1. 同一 `themeKey` 的 pending note，连续喂 4 次相关经历 → `curiosityFired` 必须停在 `maxPush`（方案甲下是 3）。
2. 第 `maxPush` 次之后仍未落判 → 该 note 的 `status` 必须是 `retired`，且 `overturnedReason` 含「追了」或「认了」（与 `spec/规格主轴.md:318` 的措辞对齐）。
3. `flash.pendingQuestions()` / `mind.ingest()` 任一路能读到 `maxPush` 或 `left`。

## G6 · `forgottenBecause` 写进了库，但导不出来

**位置**
- `src/fade.mjs:49-67` —— `freed()` 里写 `n.overturnedReason = '沉下去了：被新判断挤出的位置'`
- `src/mind.mjs:243-261` —— 写 `b.forgottenBecause = faded.droppedWhy[id]`（`src/mind.mjs:254`）
- `src/flash.mjs:27-58` —— `toNote()` 的返回对象里**没有** `forgottenBecause`
- `src/flash.mjs:148-152` —— `forgets()` 反而回去读 `overturnedReason.startsWith('沉下去了')`

**现状**

「为什么被忘掉」这个信息，内核写了**两遍**：

- `fade` 写进 `overturnedReason`（`src/fade.mjs:58`）
- `mind` 写进 `forgottenBecause`（`src/mind.mjs:254`）

但 `toNote()` 只导出了 `retiredBecause`（`src/flash.mjs:50`：`note.retiredBecause = b.overturnedReason ?? '曾经这么以为'`），**`forgottenBecause` 一个字都没出门**。同时 `forgets()` 又用 `overturnedReason` 的前缀去筛（`src/flash.mjs:150`）。

**为什么挡路**

宿主注入块里「沉下去」那一类要判断「这条是被新的挤掉的，还是被自己推翻的」——两者语气完全不同（见 `spec/插件壳.md` §3.3(c) vs (d)）：

- 被自己推翻 → 要摆三行「我以前这么以为…」
- 被新的挤掉（沉下去）→ **一行都不摆**，最多留一个空位

现在两条路（`retiredBecause` 与 `forgottenBecause`）在 `toNote()` 之后就**分不开了**：都只有一个 `retiredBecause`，而 `revision` 推翻时也会写 `overturnedReason`（`src/judge.mjs:299`）。注入层只能靠字符串前缀 `'沉下去了'` 去猜 —— **靠中文字面量判类型，是最脆的一种接法**：改一个标点就全错。

**要求改成什么**

1. `toNote()` 增加显式字段：
   ```
   forgotten: Boolean,            // 是否「沉下去了」这一类
   forgottenBecause: string|null, // 原文取 b.forgottenBecause
   ```
   并且 `forgotten` 的判定**不许用中文字面量**，改成看 `b.forgottenBecause != null`（这是 `mind` 在 `src/mind.mjs:254` 专门写的字段，语义唯一）。
2. `flash.forgets()` 的筛选条件同步改成 `b.forgottenBecause != null`，不再读 `overturnedReason.startsWith('沉下去了')`。
3. `src/fade.mjs:58` 的 `overturnedReason` 可以留（它是给人看的说明），但**不许再被任何逻辑当判据用**。

**验收判据**

1. 造一次判断性遗忘（喂一条高份量新判断挤掉低份量旧的）→ `toNote(被挤掉的).forgotten === true`，且 `forgottenBecause` 非空。
2. 造一次 `revision` 推翻（`src/revision.mjs:100-102`）→ 被推翻那条的 `forgotten === false`（它是 retired，不是 forgotten），`retiredBecause` 非空。
3. 在 `src/fade.mjs:58` 的文案里**随手改一个字**（比如把冒号换掉），上面两个单测必须**仍然通过** —— 用来证明判定不再依赖那个字面量。

## G7 · `Belief` 没有 `lastFired` 字段，冷却第一次永远不生效

**位置**
- `src/curiosity.mjs:70-72` —— 冷却判断
- `src/judge.mjs:138-171` —— `Belief` 构造函数（只初始化了 `curiosityFired`，`src/judge.mjs:158`）

**现状**

```js
if (note.lastFired != null && seed - note.lastFired <= o.cooldownBeats) continue;  // src/curiosity.mjs:70
...
note.lastFired = seed;                                                            // src/curiosity.mjs:72
```

`Belief` 的构造函数里**没有** `this.lastFired`（`src/judge.mjs:138-171` 全部字段里没有它）。所以任何一条新判断，`lastFired` 是 `undefined`，`src/curiosity.mjs:70` 的 `!= null` 直接短路 —— **第一次冷却判断永远放行，无论多久。**

**为什么挡路**

不会崩，但会让「同一悬案被同一批经历连击」：如果同一轮里连续进来几条同主题经历（这在真实对话里很常见——主人连发三条消息），一条刚出生的 `lastFired` 一直是 `undefined` 的悬案会被每一条都推一次。`spec/规格主轴.md` 没有直接对应的判据，但它会让 `curiosityFired` 涨得比实际「碰到它的次数」快，**直接歪掉 G5 里那个「第几次」的数字**。

**要求改成什么**

1. `Belief` 构造函数补 `this.lastFired = null;`（`src/judge.mjs:158` 附近，紧跟 `curiosityFired`）。

## G8 · `recall()` 的 `line` 字段会用旧 `clause()` 绕过整套形态

**位置**
- `src/flash.mjs:126-132` —— `recall()` 的 `.map(x => { ... return { ...n, score, line: clause(n) }; })`（`src/flash.mjs:130`）

**现状**

`recall()` 返回的每一条都带一个 `line` 字段，值是 `clause(n)`。而 `clause()` 现在是 G1/G2 说的那个旧形态。

**为什么挡路**

宿主注入层最自然的写法就是「拿 `recall()` 的结果，直接取 `line` 拼块」。**这会把 G1/G2/G3 的全部修正一次性绕过** —— 你在 `clause()` 里怎么改都不生效，因为 `line` 是在很久以前（还没改之前）算好存进返回对象的。

更麻烦的是，`line` 这个名字太顺手了，任何人接手都会先用它。

**要求改成什么**

**建议直接删掉 `line` 字段。** 理由：

- 它是**派生数据放在返回对象里**，会让「接口」和「渲染」耦合死；
- 注入层的形态（三行 / 一行 / 带 probe）不是 `clause()` 能表达的，`line` 表达不了、又不肯承认自己表达不了；
- 删掉之后，注入层必须显式调 `clause()` 或 `lines()`，**改哪一处就生效哪一处**。

若担心有调用方已经在用 `line`：先改成 `line: clause(n)` 保留但标 `@deprecated`，同时补 `lines: lines(n)`，一个版本后删 `line`。

**验收判据**

1. `recall()` 的返回对象**不含** `line`（或含但带 `@deprecated` 注释且仓库里零个调用方）。
2. 宿主层拼注入块时，能拿到的渲染入口只有 `clause()` / `lines()` 两者，没有第三条路。
3. 把 `clause()` 的输出故意改一个字，`recall()` 的任何字段都**不应该**再跟着变（证明派生数据不再预存）。
