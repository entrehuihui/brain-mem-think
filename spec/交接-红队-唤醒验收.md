## 一、只有一条出口

```

`followup(` 的出现次数 == 1
```

### 怎么验

**静态检查，不需要跑宿主。** 扫描插件源码目录下所有 `.js` / `.mjs` / `.ts`：

- 正则 `\.followup\s*\(` —— 命中数必须是 **1**
- 另外查 `\bstee?r\s*\(`（`agent.steer`）和 `agent\.send\s*\(`：**命中数必须是 0**，除非能证明它和出口是同一个函数的同一分支

### 允许存在的「伪命中」（列举清楚，免得误判）

- 注释里的 `followup(` —— 静态扫描时先剥注释
- 测试文件、`spec/` 下的文档
- 宿主包装层（如果将来做了 `agents.xxx` 的转发）——**如果出现，必须报出来，不许自行放过**

### 变红说明什么

**说明有第二条唤醒路径。** 从那一刻起：

- 旧插件 60 秒 6 条那个病回来
- 去重只作用在其中一条路上
- 配额落盘只记其中一半
- **块二、块四的结论全部作废**（它们都依赖「一条出口」这个前提）

### 附带的动态检查（可选，但推荐）

出口函数里必须能观察到这个顺序（不看代码，看行为）：

1. 先读 `agent.status`（`P/dsh-agent-loop/lib/index.js:790-792`，值域 `idle` / `running`）
2. `running` → **不调用 `followup`**，也不进任何队列
3. `idle` → `followup` 一次
4. 落盘成功才算完成

**断言**：把 agent 伪造成 `running`，触发 50 次唤醒，`followup` 调用数 = **0**。

> 依据：裁决七 §五-2「`running` 就这轮跳过。**不排队。** 排在队里就是『等她忙完一口气说好几句』」。

## 二、止损阀：账本不动就不许开口

### 断言（两条，必须成对）

```
A. 判断库冻结场景：跑 100 次 wake → speak ≤ 10
B. 持续真演变场景：跑 100 次 wake → speak 明显高于 A
```

**「明显高于」要量化**，建议：`B.speak >= 2 * A.speak` 且 `B.speak >= 20`。**这个阈值由 redteam 定，但一旦定了写进断言，不许回头调。**

### 怎么造「判断库冻结」

`S/wake.mjs:62-117` 的 `wake()` 输入是 `notes`（判断快照）+ `ctx.{now, lastSpokeAt, history, opts}`。**它不读消息、不读时间**，所以场景完全可控：

- **冻结**：每次唤醒传入**同一份** `notes`（深拷贝即可，内容一个字节都不变），`now` 递增加 `nextGapMs`，`lastSpokeAt` 由上一次结果驱动。
- **真演变**：每隔若干次唤醒，往 `notes` 里注入一条**真变化**——`relation` 或 `polarity` 变了算（`S/judge.mjs` 的 `changeOf` 判据），**光换说法不算**。这一点很重要：**如果 redteam 用「同主题换一句话」当演变，B 组会假绿。**

### 关键：止损阀现在**还没有**

我读了 `S/wake.mjs:19-30` 的 `WAKE_DEFAULTS` 和 `:78-91` 的三道闸：

- ① 连说两回，第三回必须停（`:82-85`）
- ② 最近 10 回沉默 ≥ 30%（`:86-91`）
- ③ 刚说完话冷却 `quietAfterSpeakMs`（`:98-100`）

**这三道闸看的全是「历史决策」，没有一道看「判断库动没动」。**

> 所以：**这个测试现在应该是红的。** 红队要做的第一件事不是写测试，是**确认它红**——红了就说明止损阀确实缺（对应裁决七 §三，已派给 kernel-dev）。
> **不要为了让测试变绿去放宽断言。** 红了就报。

### 变红 / 变绿分别说明什么

- **红（当前状态）**：止损阀缺失，冻结的账本会持续催她开口 → **正反馈环没被堵住**
- **绿**：她开口的理由是「账本动了」，不是「到点了」——**但必须同时满足 B 组**，否则绿是假的（一个永远沉默的实现也能让 A 组全绿）

### 一个反假绿陷阱（提醒）

**别只用 `speak <= 10` 判。** 一个「永远 silent」的实现能通过 A 组。**必须成对跑**，A 和 B 一起看。

## 三、时序：第二道闸是 `complete: true`，不是 suppressor

> **⚠ 这一块在 2026-10-26 晚被修正过一次。**
> 原来的断言是「除 `working-directory:current` 外无其他 runtime context」——**基于一个被推翻的假设**。
> 修正依据：`spec/定稿-命名与闸与schema.md` §2。**以那一份为准，本块按下面的新断言跑。**

> 这是裁决七 §四 点名的「命门的真相」。**优先级最高，因为它是「她看不见聊天记录」的根。**

### 3.0 先记住这个机制事实（不看懂它就会写错测试）

**`suppressRuntimeContext()` 挡不住 `working-directory:current`。**

- 那条 context 是 `required: true`（`P/dsh-working-directory/lib/index.js:44`）
- 而 `assemble()` 在 suppressed 状态下**会把 required 的再补回去**（`P/dsh-system-prompt/lib/index.js:404`）：
  `contexts: runtimeContextSuppressed ? transformed.contexts.filter((entry) => requiredContexts.has(entry.name)) : transformed.contexts`

**所以真正的那道闸是 `complete: true` 的 prompt section**（`P/dsh-system-prompt/lib/types/index.d.ts:63-69`）：
> 「restores this exact section as the sole prompt section」

实现在 `P/dsh-system-prompt/lib/index.js:403`：
```
sections: completeSection === void 0 ? transformed.sections : [completeSection],
```

### 断言（新，四条都要）

```
她通道会话的**第一轮**：
1. 系统提示 sections == 恰好一条（她的世界），且**不含** harness:identity
2. 会话历史的 user/message 里，source.kind 只允许 'mind-world'（通常一条）
3. **不许**出现任何 source.kind == 'runtime-context' 的 user/message
4. 若系统提示里出现 working-directory:current 的 context，允许；
   但它**不许**变成一条 user/message（不许落库）
```

> **第 4 条是这次新加的，也是关键**：`working-directory` 无法被 suppress，只能靠
> ① `complete: true` 让它不进 `sections`、② `pre-step` 换消息让它不进历史。
> **两道都要测。只测一道会假绿。**

### 为什么「第一轮」就够（时机问题已查清，不再是风险）

`setup(agentCtx)` 拿到的 ctx 是**已 scoped** 的（`P/dsh-agent-loop/lib/index.js:1931`：`setup?.(prepared.agent.ctx, prepared.agent)`），
而 scoped 与否决定了注册进哪个 layer：

```
P/dsh-scope/lib/index.js:190   const scope = scopeOf(ctx);
P/dsh-scope/lib/index.js:195   if (scope === void 0) layer = this.global;
```

**在根 ctx 注册 = 进 global = 对所有人生效**（灾难：所有会话都被改成只有一条 section）。

`setup` 在 `initializeAgent` 里、`publish` 之前跑（`P/dsh-agent-loop/lib/index.js:1930-1934`），第一次 `assemble()` 在 `preStep`（`:907`）——**远在其后**。
所以 **`setup` 里注册的闸，第一轮必然生效**。「第二轮才生效」这个担心可以撤掉，但**测法保留**（按 §5 的最小探针打一次日志确认）。

### 怎么造这个场景

1. 建通道会话（固定 id `mind-her`，见 `spec/定稿-命名与闸与schema.md` §1.4），`setup` 里装闸。
2. **第一轮就跑**——不能「先聊几轮再看」，要测的正是第一次。
3. 读出来：`sessionQuery.readSurface('mind-her')`（`P/dsh-session-query/lib/index.js:1168-1176`），或活会话直接 `deriveMessages()`。
4. 同时抓 `system-prompt/assemble` 事件的 `assembly.sections` / `assembly.contexts` 名字表，打日志。

### 变红说明什么（按严重度）

1. **最坏**：历史里出现 `runtime-context` 的 `user/message` → **她看见了「当前会话路径」，且这条永远洗不掉**（除非 replace 遮蔽）。**一次就毁。**
2. **次坏**：`sections` 里除了她那条还有别的（尤其 `harness:identity`）→ `complete` 没生效，她知道自己是 harness 上的 agent。
3. 中等：`contexts` 里出现 `HARNESS_SOURCE` / `WEB_SURFACE` → suppressor 没生效，多半是**注册到了根 ctx（进 global 了）**。
4. **最容易误判成红的一条**：`contexts` 里出现 `working-directory:current` —— **这条是允许的**（required，宿主设计如此）。**只看它不算红，看它有没有落成 `user/message` 才算。**

### 最小探针（如果你等不到插件实现）

`spec/定稿-命名与闸与schema.md` §2.5 有一份 60 行的临时插件，放 `D:\dsh\scratch\mind-probe\`。
**它会打印 `setup` 时刻、`assemble` 时的 sections/contexts 名单、以及每条 `user/message` 的 `source.kind`。**
一场跑通就能判 §2 的七行判读表。

## 四、白名单：她的输出不许进归档熔

> 对应裁决七 §二。**这是断掉正反馈环的上游那一下。**

### 断言（两条，都要）

```
A. 材料层：喂一段「主人说 + 她说」混合的会话进 digestSession，
   断言送给 synth 的 material 里，一条她的发言都没有

B. 判断层：跑完整一轮（digestSession → commitDigest），
   熔出来的判断文本与她的发言，相似度 < 0.86（沿用 S/digest-session.mjs:140 的阈值）
```

**A 是主断言，B 是兜底。** A 红了就是白名单没做；A 绿但 B 红，说明她自己「想」出了跟她说过的一模一样的话——**那也不能收**（可能是抄的）。

### 怎么造这个场景（关键：混合比例要拉满）

**别做「一句主人 + 一句她」这种温和样本。** 建议：

- 一段会话，**主人说 3 句，她说 20 句**（她的话占绝对多数）
- 她的话里**故意埋一条「看起来像结论」的**，比如一句带谓词、带立场的话
- 主人的 3 句**故意平淡**（没什么可熔的）

> **为什么这样造**：如果白名单没做，模型会**优先熔她那些多的、信息量大的话**——这正好是现实里的情况（她主动开口时说的一般比主人一句「嗯」丰富）。
> 温和样本会让这个 bug 假绿。

### 现状：白名单**还没有**

我读了 `S/digest-session.mjs:28-36` 的 `buildSessionMaterial`：

```
.map((m) => String(typeof m === 'string' ? m : (m?.text ?? m?.content ?? '')))
```

**它对传入的 `messages` 一视同仁，只取文本。** 谁传什么它就收什么。调用方（`digestSession`，`:112-118`）也是直接 `buildSessionMaterial(messages, opts)`，没有过滤。

**所以：这个测试现在也应该是红的。** 报红，别修。

> 顺带记一条给 kernel-dev 的接口要求：白名单要挂在 `buildSessionMaterial` **里面**（材料层），不是挂在调用方。理由——挂在调用方，将来任何一个新调用方都会绕过它。这跟 §一「一条出口」是同一个道理：**闸要装在必经之路上。**

### 变红说明什么

**正反馈环没断。** 具体后果链（写进失败报告）：

1. 她说的话 → 被当成经历 → 熔成判断
2. 判断进了库 → 心跳读到 → 觉得压得重 → 又说
3. 下一段会话归档 → 又熔 → **她的输出又被当成「她经历了这些」**

> 裁决七 原话：「她越说越确信，因为每一次说话都在给自己造证据。」
> **这个测试红了，说明这件事会真的发生。**

## 附一、`w6b_name_only`（Lead 2026-10-26 夜追加，属第四块的白名单延伸）

```
断言：
  ① 改 personaName（比如改成 '小乔'）
     → world 输出里「我是 <name>」跟着变，**其余一字不变**
  ② 改 voicePrompt / subtitle / chipHint / prefix 任意一个
     → world 输出【一字不变】。判据是 `===` **全等比较**，不是「大致一样」
```

**为什么第 ② 条必须有**：裁决八写死「名字之外，输出的每个字都必须来自判断库」。
`voicePrompt` / `subtitle` / `chipHint` 是旧插件的 UI 文案，`prefix` 是 `dsh-persona` 的人设正文。
**只要有人手滑把它们接进 `world`，第 ① 条测不出来**——名字还是对的，内容悄悄变了。

**变红说明什么**：
- ① 红 → 名字没接上配置，或 `world` 把名字写死在 src 里
- ② 红 → **有人把别人给她的设定灌进了她的世界**，直接违反裁决八
