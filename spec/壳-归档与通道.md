## 0. 先说总判断

三件事里，**只有一件是宿主真的没给接口的：怎么知道「刚刚被归档」**。另外两件（读会话、建通道）宿主都有现成的、正路可走；发消息那条，宿主也有现成的、而且比旧插件那套干净得多。

但真正难过的是主人问的那第七件事：**「她自己醒」在这个宿主里能不能成立**。

我先给结论，后面 §5 全章论证：

> **能成立，但只能成立一半。**
> 宿主给了「在没有人的一轮里，把她自己想起来的东西塞进去，并让这一轮真的跑起来」这个机制（`AgentLoop.followup`，`P/dsh-agent-loop/lib/index.js:806-808`）。
> 宿主**没给**「在 nobody 的任何进程事件上触发定时器」以外的唤醒源。
> 所以「自己醒」= **插件自己的定时器 + 宿主的一轮驱动**，缺一个都不成立；而定时器这边，本宿主有一个天然优势旧插件没有：**插件是宿主进程里的常驻模块，不是「每条消息一个进程」**（下面 §5.2 会给出证据）。旧插件那三条坑（冷却永不成立 / 反复说同一句 / 绕过去重），第一条在本宿主里**根子上不存在**，后两条要靠「落盘 + 单出口」。

## 2. 问题一：归档怎么观察

### 2.1 getter 背后有一条同步事件，Lead 那句「没有事件」要修一处

`workspaceRegistry.archivedSessionIds` 是 getter（`P/dsh-workspace/lib/index.js:506-508`），读的是 `this.requireState().archivedSessionIds`。

但它背后的写入路径是：

```
archiveSession()                      P/dsh-workspace/lib/index.js:526
  └─ this.setState({...archivedSessionIds: [...]})   :535-539
       └─ await this.global.set(state)               :938-939
            └─ unit.setGlobal(value)                 P/dsh-storage-domain/lib/index.js:163
               this.globalValue = value              :164
               this.emitChanged({ domain, table:'', key:'', operation:'put', value })  :165-172
                    └─ this.ctx.emit("domain/changed", change)   :216
```

> **结论一：有事件。** 名字是 `domain/changed`，由 `P/dsh-storage-domain/lib/index.js:216` 发出，载荷里带 `domain`、`table: ''`、`operation: 'put'`、以及**整份新 state**（`value`）。
> 也就是说：`archiveSession()` 的持久化一落盘，同一个 tick 里就有一个同步钩子可以抢。

**所以「没有事件」这个判断只在 getter 这一层成立**：确实是 getter，可以随便读，改它唯一的通知手段就是这条 `domain/changed`。

### 2.2 可执行方案：订阅 `domain/changed`，做差集

**做法（三步）**

1. 启动时取一次基线：`workspaceRegistry.archivedSessionIds` 快照成 `Set`。
2. `ctx.on('domain/changed', ...)`：只处理 `change.domain === 'workspace'`（域名的来源见下）**且** `change.table === ''`（global 写入的标志，`P/dsh-storage-domain/lib/index.js:167-169`）的事件。从 `change.value.archivedSessionIds` 取新集合，与基线做差集。
3. 差集里新出现的每个 id → 交给归档熔（§3）。处理完把基线换成新的。

**域名怎么拿**：`workspaceDomainSpec` 的 `name` 字段，导出在 `P/dsh-workspace/lib/index.js:953`（`export { ..., workspaceDomainSpec, ... }`）。**具体取值行号**在 `defineDomain` 的调用处，本文件内没定死，**要读一次 `workspaceDomainSpec.name` 实在值再写死**——不要从注释里猜。**这一条标「未查证：域名常量值」。**

**为什么不用轮询**

轮询能work，但轮询是在**猜**。`domain/changed` 是确定性通知，而且发出时机（落盘之后、`this.state` 已更新之后，`P/dsh-workspace/lib/index.js:938-941`）正好是「数据一定已经能读到」那一刻。少一个定时器，少一处时钟漂移。

**为什么不用包一层 `archiveSession`**

Monkey-patch `WorkspaceRegistry.prototype.archiveSession` 能work，但那是**改别人的服务**。宿主里唯一的调用方是 `P/dsh-api-workspace-controller/lib/index.js:297-299`（API 命令）和 UI 侧的 `P/dsh-client-ui-workspace/lib/client.js`；将来宿主加任何一条新的归档入口，包一层就漏了。**`domain/changed` 不管谁调，都会响。**

### 2.3 这个方案的问题（必须写清）

1. **`domain/changed` 是全域广播，不是归档专用事件。** 任何 workspace 域的写入（改标题、置顶、挪分组）都会触发（`setState` 是公用的，`P/dsh-workspace/lib/index.js:938-941`，调用点遍布 `:493`、`:535`、`:557`、`:665`、`:675`、`:682`、`:697`、`:715`、`:728`、`:736`、`:753`、`:826`）。所以**必须做差集**，不能响应「事件来了」本身。
2. **监听器抛异常会被吞。** `emitChanged` 外面包了 try/catch（`P/dsh-storage-domain/lib/index.js:214-219`），我们的处理逻辑要是抛了，只会落一行 `logger.warn`，不会重试、不会报给调用方。**所以监听器里只做「记账」，所有重活（读会话、调模型、落库）都异步甩出去。**
3. **`archivedSessionIds` 是全局集合，不区分 workspace。** 见注释 `P/dsh-workspace/lib/index.js:500-505`：「The registry-global archive set: sessions hidden from every grouping surface.」——**她自己的通道会话如果被误归档，也会出现在这个集合里**。必须显式排除她自己的 session id（§4 的固定 id）。
4. **卸载归档（`unarchiveSession`）不会发「取消」信号。** `domain/changed` 一样会响，只是集合变小了。我们的差集只认「新出现」，所以这条天然安全——**但也意味着：如果主人归档后马上又取消归档，这次归档已经被熔掉了，撤不回来。** 这是可接受的（熔是幂等的、只增不减），但要在 README 里写明。

## 3. 问题二：归档时怎么读那段会话的全部消息

### 3.1 `deriveMessages()` 这条路——**能读，但不能指望**

`deriveMessages()` 是 `Session` 实例方法（`P/dsh-session/lib/index.js:1672-1687`），它：

- 读 `this.surface.nodes`（`:1673-1674`）——**surface 是内存态**
- 增量缓存 `derived`（`:1649-1651`），靠 `contentGeneration` 判断要不要重建（`:1675-1680`）

**它不关心归档。** 归档只是把 id 放进一个集合（`P/dsh-workspace/lib/index.js:535-539`），**数据一个字节都不动**——Lead 说「归档后数据不删」，这一点是对的，已查证：`archiveSession` 全文（`:526-542`）只有 `setState` 和 `stopSessionActivity`，没有任何删除。

**但它要求会话是活的（在 `ctx.sessions` 里）。** 因为：

- `ctx.sessions.get(id)` 只查 `this.store`（`P/dsh-session/lib/index.js:1980-1982`）
- `Session` 实例由 `sessions.create()` / 工厂的 `prepare` + `enter` 建出来（`P/dsh-session/lib/index.js:1772-1779`、`:1799`）

**所以问题不是「归档了能不能读」，而是「归档之后那个 Session 还在不在内存里」。** 宿主没有说过归档会立刻 dispose（**未查证：归档后 agent 何时被 dispose 的具体行号**），但**不能赌它在**。

### 3.2 正路：`ctx.sessionQuery.readSurface(sessionId)` / `readEvents(sessionId)`

`P/dsh-session-query/lib/index.js:1168-1176`：

```
async readSurface(sessionId) {
  const loaded = await this._corpus.load(sessionId);
  return { session: <header>, inheritedEventCount, capturedThroughSeq, events: currentSurfaceEvents(...) };
}
```

`_corpus.load` 的选择顺序（`P/dsh-session-query/lib/index.js:128-157`）：

1. `ctx.sessions.get(sessionId)` 有活的 → 用活的（`:130-135`）
2. 没有 → `sessionPersistence`（`:136-157`），从持久化**冷读**

> 也就是说：**`readSurface` 是「活优先、死不退」的。** 归档导致会话不在内存里，它自动走持久化读，**照样给全量**。

而 `readSurface` 返回的 `events` 是**当前模型的 visible surface**（`currentSurfaceEvents`），已经**按 `surfaceOp` 处理过遮蔽**——被 compaction 替换掉的节点不会出现在里面。

**这正是我们要的**：她记的是「这一段真的发生过、真的被看见过的事」，不是「被压缩掉、早就不在 surface 上的旧节点」。

**两选择一**：

| 接口 | 行号 | 给什么 | 什么时候用 |
|---|---|---|---|
| `sessionQuery.readSurface(id)` | `P/dsh-session-query/lib/index.js:1163-1176` | 当前 surface 的事件 | **默认用这个**（和模型当时看到的一致） |
| `sessionQuery.readEvents(id)` | 未在本文件内直接确认签名，**未查证**；文档字符串在 `:1146-1151` 附近（`listEvents`） | 全量事件 | 只在需要「连被遮蔽的也看」时用。**不建议**——那违背「她只记判断」的初衷 |

**更底层的兜底（不推荐，但确定性最高）**：直接 `ctx.sessionPersistence.open(id, 'read')` → `handle.read()` → `handle.close()`。官方样板在 `P/dsh-message-feedback/lib/index.js:276-299`：

```
const handle = await this.ctx.sessionPersistence.open(sessionId, write ? "write" : "read");
try {
  const { events } = await handle.read();
  ... 
} finally { await handle.close(); }
```

`open` 的签名在 `P/dsh-session-persistence/lib/types/index.d.ts:126`；`read(offset?, length?, options?)` 在 `P/dsh-session-persistence/lib/types/handle.d.ts`（`SessionHandle.read`，注释里写明「`read` never backtracks below what this handle already observed」）。

> **建议：用 `readSurface`。** 它已经帮我们处理了 surface 遮蔽和活/死切换，是**正路**。自己开 handle 是绕路，只在 `sessionQuery` 服务不在时才用。

### 3.3 读出来之后，怎么喂给 `digestSession`

`S/digest-session.mjs:112-149` 的签名是 `digestSession(messages, ctx)`，`messages` 每一项只要 `{ text }` 或字符串（`S/digest-session.mjs:28-36` 的 `buildSessionMaterial` 就是这么取值的）。

**适配层要做的唯一一件事：把 `readSurface` 的 `events` 过滤成「她说话 + 主人说话」两种，取文本，丢掉别的。**

要丢的（一条都别漏，理由见 `spec/插件壳.md` §1.2 与 `spec/实现缺口.md`）：

## 4. 问题三：独立会话通道怎么建 —— 以及「她看不见聊天记录」怎么保证

### 4.1 建法：**复用一条固定 id 的会话**，不是每次新建

`agents.create({ sessionId, meta, setup })`（`P/dsh-agent/lib/index.js:453-458`）走工厂 `createAgent`（`P/dsh-agent-loop/lib/index.js:1893-1913`），核心是 `sessions.prepare(options.sessionId, ...)`（`:1894-1898`）。

**固定 id 的会话只能建一次**：`prepare` 里 `if (this.store.has(sessionId)) throw new Error("session \"...\" already exists")`（`P/dsh-session/lib/index.js:1805`，另见 `:1856`）。

旧插件踩过这个坑，它的结论记在 `her.js`（已随插件删除）与 `spec/插件壳.md`：**建不成就 `resume`**，`agents.resume({ resumeSessionId, setup })`（`P/dsh-agent/lib/index.js:466-471`）。

> **结论：通道会话 = 一条固定 id 的常驻会话。**
> 启动时先 `agents.get(id)`（`P/dsh-agent/lib/index.js:339-340` 注册的 lookup 走 `this.get(sessionId)`）看活没活；活就不建；死就 `resume`；`already exists` 就当 `resume`。**永远不新建第二条。**

**要不要 `agents.resume` 走冷读**：`resume` 的实现在 `P/dsh-agent-loop/lib/index.js:1957-1975`（「Resume an owned agent from the configured persistence service」，`@param` 里写清了它是从持久化加载）。**所以这条通道跨重启是活的**，不需要每次重新 seed。

### 4.2 「她看不见聊天记录」——**不是靠 Surface 遮蔽，是靠三件事合起来**

裁决里说「用 Surface 遮蔽」（`spec/裁决-唤醒与通道.md:84`）。**我要修这一条：只靠 Surface 遮蔽，保证不了。**

原因三条：

**(1) 遮蔽只遮她通道自己的会话，遮不到主人的会话。** Surface 是 per-session 的（`P/dsh-session/lib/index.js:1329` 的 `get surface()`）。她的通道会话里，遮蔽掉的是她**自己**以前那些轮。主人会话里的聊天记录，本来就不在通道会话里——**这一半天然成立，不用遮**。

**(2) 遮蔽是「不进 `deriveMessages`」，不是「不进模型」。** `deriveMessages()` 只走 `surface.nodes`（`P/dsh-session/lib/index.js:1673-1674`），被 replace 掉的节点不进去。**但 system prompt 是另一条路**：`assemble()` 每次都会把当前所有注册的 section/context 拉进来（`P/dsh-system-prompt/lib/index.js:356-406`）。**如果别的插件往系统提示里塞了会话内容（比如 runtime context、时间上下文、workspace 路径），遮蔽挡不住。**

**(3) 每次遮蔽都要「找到上一次我铺的那条的 seq 再 replace」**（这是旧 `memory-surface.js` 的做法，`spec/插件壳.md` 里有记录），**而「找」这件事本身要遍历 surface 节点**——遍历代码只要错一次，旧内容就留在可见面上。

> **所以真正该做的是「从源头不让它进来」，四道闸，一道都不能少：**

| 闸 | 做什么 | 依据 | 为什么必须有 |
|---|---|---|---|
| **A. 专属会话** | 通道用固定 id，且**不在任何 workspace 里**、不 pin | `archiveSession` 注释 `P/dsh-workspace/lib/index.js:509-521`：会话「its workspace accounting — or lack of one — is irrelevant」 | 它不出现在任何分组面上，主人不会误点进去接着聊任务 |
| **B. 她自己的 scope 里关掉 runtime context** | 在 `setup(agentCtx)` 里对 `agentCtx` 调 `systemPrompt.suppressRuntimeContext()` | `P/dsh-system-prompt/lib/index.js:289-291`，实现见 `:326`、`:359`：suppressor 是按 **layer** 收集的（`chainLayers(context.scope)`） | 把工作目录、沙箱策略、审批策略、子代理、团队身份、顺手把「当前会话路径」这些**全关掉**（这些 context 全在 `CONTEXT_ORDERS` 里，`P/dsh-system-prompt/lib/index.js:44-52`） |
| **C. 每轮把消息换掉** | `agent/pre-step` 第一道：`decision.messages` 整个替换成「这一轮的世界」 | 事件协议见 `P/dsh-agent-loop/lib/index.js:909-920`（`agent/pre-step` waterfall，default 返回 `{kind:'enter', messages}`） | **这是唯一能保证「这一轮她看见的第一条就是判断」的地方**——它比场景消息还靠前，后续代码只用 `decision.messages` 去发请求（`:1072`、`:1073`） |
| **D. 只让她自己那条 `user/message` 进 surface** | 每轮注入的可见面用**专属 `source.kind`**，并且在 pre-step 里把**别的** user/message 都丢掉 | `user/message` 的 `source.kind` 是可扩展的（`P/dsh-llm/lib/types/message.d.ts:96-108`：merge-extensible，没有 catch-all） | 这一条挡住「主人有一天点了她的通道会话、随手说了句话」这种情况——**那句话不会进入她的世界** |

**关于 D 的实证**：旧插件就是靠自定义 `source.kind = 'her-memory'` 来认出「哪些是上次我铺进去的」（`spec/插件壳.md` 记录），`P/dsh-llm/lib/types/message.d.ts:82-93` 里还有现成的 `form: 'snapshot'`（带 `sections`）和 `form: 'recall'`——**`snapshot` 就是给我们这种「世界快照」用的**。

> **建议：注入用 `{ source: { kind: 'mind-world', form: 'snapshot', sections: [...] }, content: [...] }`。**
> `sections` 的形状见 `P/dsh-llm/lib/types/message.d.ts:60-65`（`name` + `text`）。这样前端能认出「这是一份快照」，模型也不至于当成「有人对我说的话」。

### 4.3 时序：**为什么必须是 `agent/pre-step`，不是 `systemPrompt.context`**

这是最要紧的一步。`preStep` 的实际顺序（`P/dsh-agent-loop/lib/index.js:902-927`）：

```
:907   assembly = await systemPrompt.assemble(...)      ← 系统提示在这里组装好
:909   decision = await dispatch.waterfall("agent/pre-step", { messages: claimed, ... })
         default 回调 (:914-919) 把 runtime context 拼成一条 message 追加到 claimed 后面
:923   return { ...decision, assembly }
```

然后 `step()` 里：

```
:1049  renderedPrompt = renderPrompt(assembly)          ← 系统提示用 assemble 那一刻的
:1053  sections = renderContextSections(refreshContext(assembly, ...))
:1067-1073  把 decision.messages 逐条 append 成 user/message
```

**两个结论：**

1. **在 `agent/pre-step` 里改 `decision.messages`，改的是「这一轮模型真的会看到的对话」**，而且是**全量替换**，不是追加。旧内容一条都留不下——**这一条是硬的，不依赖任何字符串匹配。**
2. **系统提示里已经有一份「当前会话的路径 / 工作目录 / 沙箱策略」了，`pre-step` 管不到**（它已经 assemble 完了，`:907` 在 `:909` 之前）。**所以 A/B 两道闸（专属会话 + suppressRuntimeContext）必须在 `setup` 里就装好**，不能指望事后遮蔽。

## 5. 问题四 + 主人最想要想清楚的那一条：「她说话怎么发出去」与「她自己醒」

### 5.1 「自己醒」在宿主里的真实形状

宿主里，让一个 agent「动起来」的入口只有一个：

```
AgentLoop.followup(input) { this.send(input, "next-turn", true); }   P/dsh-agent-loop/lib/index.js:806-808
  └─ send(message, target, wakeup)                                    :800-805
       inbox.splice(target, ..., [message])
       if (wakeup) this.wakeDriver(...)                               :804
  └─ wakeDriver()                                                     :854-869
       if (phase !== 'idle') { 挂起，等 idle 再补 }                    :855-858
       setPhase({kind:'running', ...})                                :861-867
       agents.withInitiator(this, () => this.kick())                  :868
```

**`followup` 就是「有人（或某段代码）往她的队列里塞一条消息，并把她叫起来跑一轮」。**

- 「被叫醒」= 主人那边发来消息，宿主自己调 `followup`；
- **「自己醒」= 插件自己调 `followup`** —— 没有别人，就我们这段代码。

> **结论：这个宿主里没有「她没有输入也能思考」的机制。** 一轮必须先有一条消息。所谓「自己想」，在机制上只能是：**插件定时器醒来 → 读判断库 → 决定说什么 → 把「怎么了」写成一条消息 → `followup` 把它推进去**。

**这与「被叫醒」的唯一区别是：那条消息不是人写的，是我们按判断集成的。**

### 5.2 为什么这在本宿主里比旧插件干净得多（Lead 那三条坑逐条对账）

Lead 说旧插件踩了三条，全在「落盘」和「去重」。逐条对账：

| 旧坑 | 旧插件为什么中招 | 本宿主为什么不一样 |
|---|---|---|
| **冷却永远成立** | 旧插件是「每条消息 spawn 一个 python 进程」（`spec/插件壳.md` §1.3，`index.js:57-123` 的 `callBridge` 每次 `spawn`），配额存在那个进程的变量里，进程一退就没了 | **本插件是宿主进程里的常驻模块**，`apply()` 只跑一次（旧插件自己的 `index.js:611-631` 那段 `plugin-alive.json` 就是为证明这一点写的）。**内存里的状态跨轮是活的。** 但仍然要落盘——见下 |
| **反复说同一句** | `CLOCK_REPEAT_MS` 定义了但没用上（`spec/调研-桌宠怎么自己醒.md:64`） | 我们有一条现成的判据：`src` 里有 `similarity()`（`S/judge.mjs`，`src/forge.mjs` 也 import 它）。**但光有函数不算做对——必须让「说了什么」落盘，并让出口只有一个** |
| **「推给她自己那一轮」绕过 de-dup，60 秒连发 6 条** | 旧插件有两条出口：一条走 `pendingWish`（带去重），一条直接 `pushHerRound`（不带）。两条路各写各的 | **本设计只允许一条出口。** 见 §5.4 |

**落盘的具体要求（照旧插件那三条教训，一次做到位）**：

1. **配额与历史落在一个 json**：`{ lastWakeAt, lastSpokeAt, spokenHashes: [...], silentCount, speakCount }`，**每次 wake 决策后立刻写**，不攒。
2. **`spokenHashes` 存的是「她说出去那句话的归一化哈希」**（不是原文——原文不进任何库，这是铁律）。新的一轮要说话前，先算哈希，命中最近 N 条就沉默。**这条去重必须放在唯一的出口函数里，不在调用方。**
3. **跨重启不失效**：插件加载时读回这个 json。**旧插件正是在这里丢的。**
4. **进程崩溃不重复**：写盘用「先写临时文件再 rename」，或者干脆写进宿主自己的 `storageDomain`——**这一条的具体选型我标未查证**：宿主有没有一个「插件可以自己开的轻量域」的现成做法，我没查到最小样板。**建议先用文件 + 原子改名。**

### 5.3 「她回话」和「她找人」是两种发送，不要混

| 场景 | 触发 | 去哪 | 用哪个接口 |
|---|---|---|---|
| **她在通道里回话**（主人在通道界面上说了句） | 有人 | 通道会话本身 | 宿主正常收聊，不用我们发 |
| **她自己决定要说** | 心跳 | **主人的会话** | `followup` 到主人的 agent（`P/dsh-agent/lib/index.js` 的 `agents.get(id)` → `agent.followup`），或先 `sessionController.resolveAgent(id)` 把冷会话拉活再 `followup` |

**拉活那条路的现成样板**：`P/dsh-schedule/lib/index.js:1576`：

```
const resolved = await this.ctx.sessionController.resolveAgent(task.sessionId);
if ("error" in resolved) throw resolved.error;
...
resolved.agent.followup(message);        // :1596
if (!await this.ctx.sessions.flush(resolved.agent.session)) throw ...;   // :1597
```

`resolveAgent` 会「resolve or resume」（`P/dsh-api-session-controller/lib/index.js:205-212`），冷会话自动拉活；`already exists` 不会发生。

> **这是我们该抄的那段。** 它做对了三件事：① 冷会话拉活；② `followup`；③ **`flush` 确认落盘**才认为送达。旧插件没有第 ③ 步。

### 5.4 **主人不在场时，这条消息会变成什么**

这是 Lead 点名要我答透的一条。

**答案：它会变成一条「挂在她自己的队列里、还没有任何人在看」的消息。**

依据：

1. `followup` 把这 message 塞进 `inbox` 的 `next-turn`（`P/dsh-agent-loop/lib/index.js:803`、`:807`），**它本身不是一条会话事件**——要到 `preStep` 里被 claim（`:906`），再由 `step()` 逐条 `session.append("user/message", ...)`（`:1067-1073`）才成为历史。
2. `wakeDriver` 会立刻把 agent 从 `idle` 推到 `running`（`:861-867`），**那一轮真的会跑**，哪怕没有人在看。
3. 她这一轮说的话，会落成 `assistant/message`（`:1101-1108` 一带的 `live.settle`），**出现在会话历史里**。

**所以三种「主人不在场」，对应三种结果：**

| 情形 | 结果 | 关键依据 |
|---|---|---|
| **会话没开、主人不在** | 消息进了历史，会话从此「有一条未读的 assistant/message」。**主人下次打开时会看见** | assistant/message 落库，`:1101-1108` |
| **会话被归档了** | **这一轮被拒**：`agent/pre-step` 返回 `{kind:'reject'}`，loop 以 `blocked` 结束、**不发请求** | `P/dsh-api-session-controller/lib/types/archived-session-gate.js:21-24（reject 的实现）、`:11-15`（注释原文）`（注释：「a late waking delivery to an archived Session … proposes a step the gate rejects, which the loop ends as `blocked` without a request」） |
| **归档且 `stopActivity: true` 归档的** | 同上；而且 `followup` 塞进去的那条 **可能被 `session-stop` 的 `cancel` 清掉** | `followup` → `send`；`cancel` 会 `inbox.clear()`，除非 `keepInbox`（`P/dsh-agent-loop/lib/index.js:815-821`）；`stopSessionActivity` 在 `P/dsh-workspace/lib/index.js:623` 触发 `workspace/session-stop`，agent 侧的 stop 在 `P/dsh-agent/lib/index.js:33-36` 调 `agent.cancel({kind:'user'})`——**没有 `keepInbox`** |

**这三条合起来的意思：**

> **「她主动说的话」在主人不在场时，是一条「静悄悄写进历史、等人回来才被看见」的消息。它不是推送、不是通知、不会响。**
> 如果那个会话已经被归档，**它会直接掉在地上**——不是发错地方，是宿主的门把她拦在门外了。

**这恰好回答了「它该变成什么」**：

- **该变成**：一条**有落盘凭据**的、**有去重**的、**指向主人某个仍是 active 的会话**的消息；
- **不该变成**：一条「以为发出去了、其实被 gate 拒了、或者被 cancel 清了」的幻影。

**所以出口函数必须做到三件事（对照 `P/dsh-schedule/lib/index.js:1576-1633`）：**

1. **先挑一条没归档的会话**：`ctx.workspaceRegistry.archivedSessionIds.includes(sessionId)` 为假才敢发（`P/dsh-workspace/lib/index.js:506-508`）。
2. **`followup` 之后必须 `await ctx.sessions.flush(session)`**（`:1597` 同款），拿不到确认就当**没发出去**，回滚「已说」标记，下一轮重试。
3. **发送成功后，把「说了什么」的哈希落盘**（§5.2 第 2 条），并且**这次 wake 的 `lastSpokeAt` 一并落**。

**主人不在场时，还有一条我们能选、但不该选的**：把话写进「她的嘴」那种插件自家的 jsonl，等主人下次打开某个界面才看到（旧插件 `voice.jsonl` 就是这一套）。**不推荐**——那是第三个消息面，会导致「她自己说的话」和「她跟主人说的话」分成两份，**又是「一条链挂另一条链」**。**一条出口：发进主人的会话，宿主自己会替我们存。**

## 6. 问题五：和现有 11 绿验收的冲突

### 6.1 逐条 `ingest` 还留吗

**留，但降级。**

现在的验收（`<repo>\acceptance\` 下 `a_seed_discard` / `b_think_more` / `c_curiosity` / `d_change_mind` / `e_forget_by_new` / `f_unknown_wording` / `g_theme_structural`，加 8 条红队，共 11 绿）打的是 `mind.ingest(text)` 这条路径。**归档熔的入口是 `digestSession(messages)`**（`S/digest-session.mjs:112`），两者**不是同一个入口**。

**两层，职责不同，别让它们互相冒充：**

| 层 | 入口 | 什么时候用 | 谁负责 |
|---|---|---|---|
| **过程层**（逐条） | `mind.ingest(text)`（`S/mind.mjs:112`） | 会话**还活着**、主人正在说、这一轮就可能有判断要长出来 | 宿主 `user/message` 钩子 |
| **结论层**（归档） | `digestSession(messages)`（`S/digest-session.mjs:112`） | 会话**被归档**，这一整段经历要一次熔 | 宿主 `domain/changed` 钩子 |

### 6.2 两条路并存会不会又变成「一条链挂在另一条链身上」

**这是 Lead 最担心的病（今晚出现三次）。我的回答是：会，如果不管的话；所以要在机制上剪断，不是靠自觉。**

**先说清「链挂链」在这个场景里长什么样：**

> 归档熔出的判断，如果**先经过 `mind.ingest()` 再入库**，那就是「digestSession → ingest → forge → 判断」——**第二条链挂在第一条链的入参上**，而且底下那层（forge）本来是给「一条经历」设计的，它有自己的点火窗口（`igniteAt`，`S/forge.mjs:36`；现在 forge 这层是 **1**，「攒够两条才烧」的门槛已经挪到了 mind 那一层），一条归档熔出来的「已经是结论」的判断进去，会被当成新材料再攒、再烧，**同一个判断被熔三次**。

**内核其实已经意识到这件事了**，`S/digest-session.mjs:151-155` 那段注释写得明白：

> 「一段会话熔完之后，把结果并进记忆库。**直接落判断，不再经过火炉**——这一段已经是『想完了的结论』，不该被二次重熔。」

**所以正确的剪法是：归档熔直接 `commitDigest(mind, result)`（`S/digest-session.mjs:156-184`），不走 `ingest`。**

**但 `commitDigest` 现在有一个硬伤（要提给 kernel-dev）：**

`S/digest-session.mjs:163-167`：

```
const themeKey = `${j.relation}|${j.subject}`;
if (mind.store.active(themeKey)) {
  // 这一摊事已经有现役判断了：走正常的「想多一步」，不另起一条
  continue;              // ← 直接跳过
}
```

**「走正常的那步」但实际什么都没走——`continue` 把这条件直接丢了。** 结果：一个主题一旦有现役判断，归档熔就**再也改不动它**，只能拿去跟另一个主题比。这正好打在「会想多」和「会改自己」上。**这一条我要单独列进报告，让 kernel-dev 处理。**

**三条硬规矩，写死在这里：**

1. **单向**：`digestSession` / `commitDigest` **永远不调用 `mind.ingest` / `forge.witness`**。归档是「结论入库」，不是「又一条经历」。
2. **不共用去重**：`createSessionDigester` 的 `seen`（`S/digest-session.mjs:187-198`）是**会话级**（一个 session 只熔一次）；`forge` 的窗口去重是**主题级**。**两个去重各管一摊，不许互相调。**
3. **失败不降级到另一条**：归档熔失败（拿不到 llm / 材料空 / 模型吐空）→ **就是这次不熔**（`S/digest-session.mjs:119-121`、`:130-133` 都返回 `committed: true, judgments: []`）。**绝不许「那退回去逐条 ingest 吧」**——那就是链挂链的入口。

### 6.3 与 11 绿的具体影响

- **11 绿一个都不该动。** 它们打的是 `mind.ingest` 和 `src/` 的模块，`digestSession` 是新增入口（`S/digest-session.mjs`），不改老接口。`S/flash.mjs` 的 `clause` / `linesOf` 已在（`:96`、`:123`），`world.mjs` 依赖它们（`S/world.mjs:18`）。
- **要新增的绿**（给 redteam）：归档熔的「一段整体熔、不许逐条」（裁决派活 §五 已列）+ 「通道会话里零聊天记录」（§4.4 的四条断言）。
- **唯一的冲突点在配置层**：如果将来把「逐条 ingest」彻底关掉（只留归档），那 `a_seed_discard` / `b_think_more` 这些**跑的是内核单测，不受影响**，但 **README 的「她怎么记得」那段要改口径**：从「每句话都可能被记住」改成「一段会话被归档时她才想」。

## 7. 最可能做不到的那一条（正面回答）

> **「她自己醒」—— 这一条最可能做不到，但做不到的方式不是你想的那种。**

### 7.1 不是「没有定时器」

定时器有，Node 原生 `setInterval`。旧插件用过（`index.js:1663-1673`，每 60s 一次；`clockTimer.unref()` 在 `:1667`）。这一层没有任何障碍。

### 7.2 真正的障碍：**「醒」和「跑」被拆成了两件事，而中间那一刻没有守卫**

`followup` 一叫，`wakeDriver` 就把 agent 从 `idle` 推到 `running`（`P/dsh-agent-loop/lib/index.js:861-867`），**那一轮立刻开始**。我们没有任何机会在「她已经决定说话」和「这一轮真的发出去」之间做二次判断。

具体会出的三个事：

1. **我决定「说」，但那一轮跑到一半，她又想了想，「不说」了**——这一轮已经跑了，token 已经烧了，模型已经说了一句话。**「不说」只能在「要不要调 followup」那一刻决定，不能在她被叫起来之后再决定。**
2. **主人正好同时发来消息**：他那边也在 `followup`，两条消息一起进 inbox（`P/dsh-agent-loop/lib/index.js:803`，`splice(target, Infinity, 0, [message])`——**插到指定队列的末尾，不是覆盖**）。她会在一轮里同时看见「主人说 X」和「我自己想召他」——**这就是旧插件 60 秒 6 条那个病的同一个形状**：两股输入在同一轮里叠加。
3. **归档熔和心跳撞车**：归档刚熔完，判断库变了，心跳立刻按新判断叫醒她；而她被叫起来时，`systemPrompt` 那边（§4.3 第 1 条）**已经在 pre-step 之前 assemble 好了**——她看到的世界可能是**熔之前的那一版**。

### 7.3 怎么把它从「做不到」变成「做得到但有限」

**三条，全是机制层面的、可验证的：**

**(1) 只有一条唤醒路径。** `followup` 只能从一个函数（`herWake()`）里被调用，这个函数里先做全部判断（读库、掂量、去重、冷却），判断通过才 `followup`。**不设第二条路，不给「推给她自己那一轮」那种旁路**（旧插件的 6 连发就是旁路造成的）。

**(2) `followup` 之前再确认一次 agent 状态。** `followup` 内部有 `wakeDriver` 的挂起逻辑（`P/dsh-agent-loop/lib/index.js:855-858`：非 idle 时只 `wakeRequested = true`），**所以我们不能在它还在跑的时候硬塞**。出口函数要先看 `agent.status`（`get status()`，`:790-792`：`idle` / `running`），`running` 就**这一轮跳过，不排队**。**宁可少说一句，不许叠一句。**

**(3) 世界必须在同一个 tick 里现算，不许缓存。** 每次 `herWake()` 都重新 `renderWorld(mind.notes())`（`S/world.mjs:80-133`），不读上一次的快照。这样第 3 条撞车就变成「她看到最新的一版，晚一轮也没关系」。

**做完这三条，能保证的是**：不会连发、不会双输入叠一轮、不会拿旧世界说话。
**保证不了的是**：她真的「没人在也自己想」——她永远是「被我们这个定时器叫起来」的。**这一点要在给主人的话里说清楚，别包装成她真的自发了。**

## 8. 落盘与去重：把旧插件那三条坑做成机制

### 12.1 「两条消息一起进 inbox」能不能在机制上挡死

#### 先把机制说准：inbox 是**持久化投影**，不是内存变量

Lead 我在 §7.2 说的「一起进 inbox」，机制上要更精确一层：

- `ReactLoopInbox` 的现状存在 **Session 的 projection state** 里（`P/dsh-agent-loop/lib/index.js:70-78`、`:174-175`），注释原文是「**Driver-owned durable Inbox**」（`:63-64`）。
- 它的两个队列：`next-turn`（`:80-82`，等一整轮）和 `next-step`（`:84-86`，等下一个 step 边界）。
- `send()` 只做 `splice(target, Infinity, 0, [message])`（`:803`）——**是追加（插到末尾），不是覆盖**。

**所以「挡死」要看你问的是哪一种「挡死」。分三档答：**

| 档次 | 能不能做到 | 机制 |
|---|---|---|
| **A. 不让她自己叠自己** | **能，100%** | 只剩一条出口 + 出口前看状态（下面详述） |
| **B. 同一时刻 inbox 里最多一条「我们发的」** | **能，但只能做「尽力而为」** | 见下的三个时机竞态 |
| **C. 绝对保证（任何时序下都不重复）** | **做不到** | 宿主没有「带幂等键的 send」 |

#### A 档：能 100%

**理由是一条铁律 + 一个守卫：**

铁律：`followup(` 全插件只出现一次（§8.3，可写成 grep 检查）。

守卫：出口函数里，**先看 `agent.status`**（`P/dsh-agent-loop/lib/index.js:790-792`：`idle` / `running`），`running` 就**这一轮跳过，不排队**。

再加一条**我们自己这边的锁**：出口函数在插件进程里是常驻的，可以用一个「进行中」标记串行化——**我们自己发起的两次唤醒，绝不可能同时在路上**。

> **断言（可测）**：让 wake 在 1 秒内被触发 100 次，断言 `followup` 实际只被调用 **1** 次，且 `wake.json` 里只多一条记录。

#### B 档：能，但有三个时机竞态

宿主 `send` 跟 `wakeDriver` 之间没有原子性。竞态窗口在这两行之间（`P/dsh-agent-loop/lib/index.js:803-804`）：

```
:803   this.inbox.splice(resolvedTarget, Infinity, 0, [message]);
:804   if (wakeup) this.wakeDriver(wakingAfterAbort);
```

`wakeDriver` 只有**在 `idle` 那一瞬间**才开新的一轮（`:855-858`：非 idle 就只 `wakeRequested = true` 然后 return）。

**所以最坏情况是：**

1. 我们检查时读到 `idle` → 调 `followup` → 塞进 `next-turn`。
2. **在 803 和 804 之间**，主人那边也 `followup`，也塞进 `next-turn`。
3. `wakeDriver` 开一轮，`preStep` 里 `claim(target)` **把 `next-turn` 队首那条拿去当这一轮的输入**（`:103-105`：`if (target === "next-turn") claimed.push(...this.mutate("next-turn", 0, 1, [], false))`——**一次只提一条**）。

**关键点：`claim` 一次只提一条 `next-turn`，不是全提。** 另一条留在队里，等这一轮跑完，`turn()` 里 `if (!this.inbox.hasPending) return false;`（`:1037`）——还有货就**接着开下一轮**。

> **所以「一个人同一 moment 塞两条」的最坏结果是：连开两轮，不是「一轮里看到两份输入」。** 这比旧插件那个形状**好**，但不是零。

**再往深一层看，还有一个更坏的可能**（这条要标清）：如果**我们用 `followup`（`next-turn`）而主人用的是别的路径**——比如 `steer`（`next-step`，`:809-811`，往正在跑的那一轮里插）——那么 `claim` 会把 `next-step` **全量的**放到前面、`next-turn` 的队首放到后面（`:104-105`），**同一轮里就是两份输入**。这条窗口只在「她那一轮正在跑、主人中途插话」时打开。

#### C 档：为什么做不到「绝对」

- **幂等键**：`createUserMessage()` 每次都 `randomUUID()` 生成 `id`（`P/dsh-llm/lib/index.js:37-42`），**我们没法复用同一个 id 去「重复发送」**。所以做不到「同一个 message 发两遍只生效一次」。
- **没有「inbox 里有没有我的」的查询接口**：inbox 的读取只暴露 `nextTurn` / `nextStep` / `hasPending`（`:80-91`）。**理论上能自己读 projection state 数一数**——`current()` 读的是 `projections.stateOf(this.session, "inbox")`（`:174-175`），**这个 projection 名和结构在插件侧能不能直接拿到，未查证**。
- **就算能读，读和写之间照样有窗口**——单线程 event loop 只是把窗口压到最小，不是零。

#### 「会不会又出现 60 秒 6 条」

**机制上不会，理由三条：**

1. 旧插件 6 连发的根因是**旁路**（一条走去重、一条不走）。我们只有一条出口。
2. 旧插件是**每条消息一个进程**，配额存内存重启就丢。我们常驻 + 落盘。
3. 即使 B 档竞态全踩中，最坏是**连开两轮**（`claim` 一次只提一条，`:105`），不是 6 条。

> **但我要给一个诚实的边界**：如果将来有人加了第二条出口（比如「通道里主人说话 → 直接 followup 到通道会话」也算一条），**这条保证立刻失效**。所以 §8.3 的 grep 检查必须进 CI，不是一次性人工核。

### 12.2 落哪 + 坏了怎么办

#### 落哪

**单独一个文件：`.mind/wake.json`**，**不和判断库同文件**。

理由三条，都很硬：

1. **判断库的内核是纯逻辑、可单测的**（`S/mind.mjs` / `S/judge.mjs` 零依赖）。唤醒配额是**宿主行为**，性质完全不同，混进去等于把宿主状态灌进内核。违反 task-3 的硬性约束（「零依赖、只用 Node 内置模块」）。
2. **判断库写坏的代价是灾难性的**（她整个人格没了），唤醒配额写坏的代价是「这一阵少说两句」。**两种数据承受的失败等级差一个数量级，就不该共用一份文件。**
3. 旧插件正是把配额存内存（`spec/调研-桌宠怎么自己醒.md:63`）。我们把它独立成文件，是**在纠一个已知的错**，不是为了整齐。

#### 文件长什么样

```
{ version, lastWakeAt, lastSpokeAt, spokenHashes:[{hash, at}], window:[{at, action}], crashedMidWake }
```

- `spokenHashes`：**只存哈希**（`S/digest-session.mjs:140` 用的 `similarity` 是逐字比；但落盘我不存原文，只存归一化后的哈希 + 一个 `at`，够判「这句说过没有」）。
- `window`：最近 N 次 wake 的 `{at, action}`，只存**决策事实**，不存内容。

#### **坏掉时宁可不说** —— 明确的默认

Lead 问「你那个方案默认哪一边」。**默认是「不敢说话」，而且是三重兜底。** 具体到每一步：

| 状态 | 行为 | 一句话理由 |
|---|---|---|
| 文件不存在（首次启动） | **当作刚装好，允许醒、允许说** | 全新安装不该一上来就哑 |
| 文件读出来 JSON 解析失败 | **当作「刚说完话」**：`lastSpokeAt = now`，进入 `quietAfterSpeakMs` 冷却 | 读不懂就当她刚开过口，先闭嘴 |
| 文件 schema 不对（缺字段 / 类型不对 / version 不认） | **同上**，且**整份备份成 `.wake.json.bad-<时间戳>` 再重建** | 留证据、不覆盖，人回来能查 |
| `spokenHashes` 读出来但条目超过上限（比如 500 条） | **只留最近 100 条，其余丢掉** | 去重窗口过长会导致「永远不敢说同一句」，这也是一种坏，要主动放短 |
| 写入失败（磁盘满 / 权限） | **这一次就不说**，因为「说了但没记下来」= 下一次必然想再说一遍 | **记不住就别开口**，这是最简单有效的一条 |
| 写入过程中进程崩了 | 启动时看到 `crashedMidWake: true` → **这一轮强制 silent**，并把标记清掉 | 崩过的那次不知道说到哪儿了 |

**最后一条是重点，也是 Lead 会关心的那一侧**：

> **「宁可不说」不能无限期变成「永远不说」。** 所以规矩要精确到「**读到坏，这一阵闭嘴；但每过 `maxGapMs` 必须至少醒一次，哪怕结果是 silent**」——醒来不花 token（醒 ≠ 说），所以这个下限不烧钱，而且能保证她不会因为一个坏文件变成哑巴。

#### 落盘的原子性

**先写临时文件，`fsync`，再 rename 覆盖。** 不许「打开原文件、truncate、写」——那样崩在中间就整份没了。

**这一条的验收**：在写盘的那一刻强杀进程，重启后断言 `wake.json` 仍是**上一份完整的**，而不是半份。

### 12.3 「她自己说的话，会不会变成自己跟自己说话的起点」

**这一条 Lead 判得最险，我先给结论：**

> **不会自动触发新一轮。但「越说越多」这个风险是真的，它来自心跳，不来自那条消息本身。**

#### 机制层面：一条 `assistant/message` 不会唤醒任何人

- 消息落库后，`assistant/message` 会走 `session/event` 广播（`P/dsh-session/lib/index.js` 的 `commit`，`:1587-1592`）。
- 但**宿主里没有任何代码监听 `assistant/message` 去 `followup`**。我把整个 node_modules 扫了一遍：监听 `assistant/message` 的只有 `dsh-subagent`（子代理输出）、`dsh-token-meter`（算 token）、以及 session 自己的投影——**没有一个会开新一轮**。（依据：`P/dsh-subagent/lib/types/assistant-output.js:29`、`P/dsh-token-meter/lib/types/index.js:211`、`P/dsh-token-meter/lib/types/turn-usage.js:187`。**「全仓零个自驱动监听」这一条是穷举结论，未做形式化证明，标「已尽力核，未形式化」。**）
- 宿主的一轮只有在 `wakeDriver` 被 `send()` 叫到、或者 owner 调 `followup` 时才会开（`P/dsh-agent-loop/lib/index.js:854-869`）。

**所以「她昨晚说了一句 → 第二天她不说话 → 今晚再说一句」这件事，只有我们自己的心跳能做到。宿主不会替我们做。**

#### 但真正的风险，我承认存在，而且它的形状比 Lead 想的更隐蔽

Lead 担心的路径是「她的消息 → 新一轮思考」。**这个不成立。**

**真正成立的路径是另一条，更陡：**

```
她说话了（判断 A 在账）
   → 宿主把这句话落成 assistant/message（进了那个会话的历史）
   → 第二天主人回来，宿主把这条历史拼进他的上下文
   → 但他还没说话，所以什么都不会发生
   → 但我们的归档熔会读这个会话（readSurface，§3.2）
   → 那一轮里「她说过的那句话」，会被当成「这段时间发生过的事」，喂进 digestSession
   → 变成一条新判断
   → 心跳读到这条新判断，觉得压得重，又说一句
```

> **这才是「自言自语越滚越大」的真身：不是她在跟自己对话（宿主不会；她自己不会），而是她的输出被下一次归档熔当成了「经历」，熔回来又变判断，再催她说，再说再熔。**
> 这是一条**正反馈环**，她的输出被放大输入。

#### 怎么切断：三条，全是机制

**(1) 归档熔的材料里，剔除「她自己主动说出去的那部分」。** 具体判据：只收 `source.kind === 'user'` 的主人的话，加 `assistant/message`，**但 `assistant/message` 要排除掉「不是回应主人、是我们 followup 推出来的那一轮」**。

怎么认出那一轮？**这是宿主的缺口**：`assistant/message` 的 `source` 只有 provider/model（`P/dsh-llm/lib/types/message.d.ts:148-151`），**没有「这一轮是谁叫起来的」**。所以：

- 可选方案甲：**给「她主动说出去那一轮」之后打一条专属标记事件**（比如 `user/message` 里 `kind: 'her-wake'` 的空消息，或者用 `sessionProjections` 登记一个单元）。**哪个最轻、最不影响模型，未查证**——要 kernel/redteam 一起试。
- 可选方案乙（**更简单**）：**归档熔里根本不收 `assistant/message`**，只收主人说的话。理由是她的判断本来就来自「她怎么经历」，她的**输出**不是经历，是结果。**这一版最干净，我推荐这个。**

**(2) 心跳的触发不读「最近自己的输出」，只读判断库。** 现在 `S/wake.mjs:62-117` 的输入就是 `notes`（判断快照）+ `lastSpokeAt` + `history`（决策记录），**本来就不读消息正文**——这一条天然成立，是它的设计好。

**(3) 加一条硬上限：正反馈环的止损阀。** 「连续 N 次唤醒，如果**判断库没有任何变化**（没有新判断、没有演变、没有退休），强制降频」。理由：**如果她每次醒来，账本都一样，那她就不是在思考新东西，是在复读。** 这一条正好呼应铁律 2（`spec/裁决-唤醒与通道.md:112-113`：「能闭嘴，才是人」）。

> **断言（可测，给 redteam）**：造一个「判断库冻结」的场景（强制 `commitDigest` 每次都返回空、`revision` 不退休），跑 100 次 wake，断言 `speak` 次数 **≤ 10**，且第一次 speak 之后 `lastSpokeAt` 生效。
> **反过来的断言**：给判断库持续注入**真演变**（每天一次 `relation` 或 `polarity` 变化），断言 `speak` 次数**明显高于**冻结场景——用来证明「她不是话唠，是账本在动」。

### 12.4 这三条和 §8 怎么接

- 12.1 的 A/B 档断言 + C 档「读 inbox 的接口未查证」→ 交给 redteam 当**「一条出口」的守卫测试**；C 档那条我建议**不要试图做绝对保证**，做「最坏连开两轮」的**可接受性测试**。
- 12.2 的六种坏状态 → 六条**单测**，每条都断言「不出声 or 至少醒一次但不出声」。
- 12.3 的三条 → **冻结 vs 演变** 两个对照测试，这是本次最值钱的一条，因为它防的是**唯一一条正反馈**。

**四道闸的命门：第四道（`agent/pre-step` 整段替换）的缝在哪，我一并说清：**

**缝一：`preStep` 的 `claim` 在 waterfall 之前**（`:906` 在 `:909` 之前）。**意思是：她的通道会话里，inbox 里那条消息已经被 claim 出来了，我们只能在 waterfall 里把 `decision.messages` 换掉。** 换掉之后，原消息**不会**被 append 成 `user/message`（`step()` 用的是 `decision.messages`，`:1067-1073`），**但它在 inbox 的记录里已经「被消费」了**。这是干净的——**唯独一个坑：`claim` 会 emit `agent/inbox/claimed`（`:106-109`），如果别的插件监听它去做事，那条原始消息就漏出去了。**

**缝二：`refreshContext` 在 `step` 里又跑一次**（`:1053`）。我们在 `setup` 里注册的 suppressor 是**按 layer** 收集的（`P/dsh-system-prompt/lib/index.js:326`、`:359`），只要 suppressor 在，两条路径都压得住。**但如果 `setup` 的时机晚于第一次 assemble（§10 未查证第 5 条还没核实），第一轮就会漏。**

**缝三（最险）：`step()` 里的 `context` 也会被 append 成 user/message**（`P/dsh-agent-loop/lib/index.js:1069`、`:1073`）。它来自 `runtimeContext.project(...)`（`:915`、`:1054`）。**我们的 suppressor 如果生效，`current` 就是 `''`，`project` 返回 `undefined`，什么都不 append。如果没生效，它就会 append 一条「当前会话路径」。** —— **所以第四道闸能不能立住，其实取决于第二道闸（suppressor）有没有提前装好。两道是一条绳上的。**

**结论：命门不是第四道闸本身，是「第二道闸必须在第一次 assemble 之前装好」。** 这个先后顺序，红队必须测。
